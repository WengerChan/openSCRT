# 复盘：CI 打通过程中的 101 次失败

本文记录 openSCRT 从"首次提交"到"三平台全绿"之间每一次失败的**真实根因**与**可执行的预防规则**。
规则不是感想——每条都对应一次实际浪费的排查轮次，并在 `AGENTS.md` 中被固化为硬约束。

时间跨度：2026-10-21 ~ 2026-10-25。GitHub 的记录里这段一共有 **101 次失败的 run**（含发布流水线）；
本文逐条挖过根因的是其中 42 次：第一轮 21 次（Phase 0 门禁打通三平台），第二轮 7 次
（Phase 1 收尾：工作区外壳 + CI 内真实 SSH + TSan 门禁 + 与 tmux 的差分基线），
第三、四轮 14 次（Windows 本地 shell 通道零输出、它的关闭死锁，以及发布流水线的打包失败），
见文末「第三轮」「第四轮」。

## 根因一：把"工具报告成功"当成了"产物在预期位置"

**症状**：vcpkg 连续 12 轮输出 `Installing 3/4 gtest... Elapsed time to handle gtest: 17 s`，
而 CMake 在同一路径下报 `Could NOT find GTest`。

**错误推理链**（当时的我）：
1. "vcpkg 报告安装成功 → 文件在 `vcpkg_installed/x64-linux/lib/`"
2. "CMake 找不到 → 前缀路径没生效"
3. 调 `CMAKE_PREFIX_PATH` → 仍失败
4. 查 vcpkg port 源码，确认有 `vcpkg_cmake_config_fixup` → "配置包肯定装了，是 CMake 找不到"
5. 切到 CMake 内置 `FindGTest` 模块模式 → 仍失败
6. 钉 CMake 版本、关 manifest 模式……每一步都在调"CMake 怎么找"

**真相**：`ls` 一次就知道——安装根目录**存在，但是空的**。vcpkg 装到了别的地方，
而我调了 6 轮"在哪里找"，没有一轮去确认"东西到底在不在"。

**预防规则**：
> 任何"工具报告成功，但下游找不到"的场景，第一反应必须是 `ls -R <路径>`，而不是调整下游的搜索参数。
> 排障顺序永远是：**产物存在吗 → 路径对吗 → 工具怎么找**。跳过第一步是最大的浪费来源。

## 根因二：假设不可证伪，于是连续被日志推翻三次

三次"看起来很有道理"的推理，全部被下一轮日志直接推翻：

| # | 假设 | 证伪它的日志 |
| :--- | :--- | :--- |
| 1 | 移除 `pybind11` 就能止住 CPython 构建 | 下一轮 CPython 仍在编译——它是被 vcpkg 当 **host 依赖**拉进来的，与目标依赖无关 |
| 2 | 显式传 port 名 = classic 模式 | `error: In manifest mode, vcpkg install does not support individual package arguments.` |
| 3 | CMake 4.4 破坏了 vcpkg 的前缀路径处理 | 钉到 3.31.12 后**错误一模一样** |

第 3 条尤其值得记：我先看到 `cmake-4.4.4-...` 出现在报错路径里，就顺势推断"CMake 4 有问题"。
但那条路径只说明**用了哪个 CMake**，不说明**它导致了失败**。我用一个观察替代了一个因果。

**预防规则**：
> 每个假设必须先写成"如果为真，日志里应该看到 X"，再去看日志。
> 如果一条日志同时能解释"假设成立"和"假设无关"，它就不能作为依据。
> 连续两轮修同一处失败而症状不变时，停下推理——进入观测模式（见根因一）。

## 根因三：失败的测试里混着"测试自己写错了"

第 19 轮单测首次运行，4 个失败中有 **3 个是断言写错**，只有 1 个是真 bug：

- `SurvivesRepeatedWrapAround` **先读后写**，而缓冲区初始为空，burst 0 必然失败；
  构造输入时又写成 `vector(count, value)` 且参数用反了（MSVC C4267 报的正是这个）
- `AutoWrapAfterLastColumn` 放入 `'A'` 却断言小写 `"a"`
- `WideGlyphWrapsRatherThanSplittingAtMargin` 用了 3 列网格，`'A'` 之后还剩两列，宽字符**放得下**，根本没触发换行
- `DefaultCapacityMatchesRoadmapMaximum` 断言恰好 128000，但环形缓冲按页对齐只能取 131072

如果按"测试红了就改代码"的惯性处理，这 3 个会被改到"通过为止"，真实 bug 反而被淹没；
如果按"测试红了就是代码错"，又会去给生产代码打补丁。

**预防规则**：
> 测试失败时，先判断**是断言错还是实现错**，逐条判断，禁止批量修改期望值。
> 一个失败里同时存在两类根因是常态——把两者记在同一处 commit 里是好的，但**必须逐条写明理由**。
> 自查信号：如果一次改动里有 3 个以上测试期望值被修改，说明正在用"改期望"代替"改实现"。

## 根因四：跨平台的可移植性假设

四次失败，同一类根因——**在本机成立的假设在别的平台不成立**：

| 假设 | 实际 | 后果 |
| :--- | :--- | :--- |
| `mapfile` 可用 | macOS runner 的 `/bin/bash` 是 3.2，**没有 mapfile** | exit 127 |
| 文本模式写文件是 LF | Windows 上 Python `open(w)` 产出 **CRLF** | `\r` 混进 vcpkg package spec |
| preset schema `version: 6` 接受当前字段 | `outputOnFailure` / `timeout` 是 **v7** 才有的 | CMake 拒收整个文件 |
| 依赖装在 CMake 被告知的位置 | 见根因一 | 整条链断裂 |

**预防规则**：
> CI 脚本里禁止 `mapfile`/`readarray`/数组展开；用 `while IFS= read -r` 并显式剥 `\r`。
> 写给 CI 读的文件一律 `newline="\n"`。
> preset 文件的字段必须与声明的 `version` 严格对应，改 schema 就改 version。
> 涉及"另一端读什么"的路径，**由写入方显式指定**，绝不依赖默认值。

## 根因五：工具链版本用开放区间，等于没有锁

`cmakeVersion: '>=3.28.3'` 实际解析到 **4.4.4**。vcpkg 工具链锁在 2025-09 基线，
CMake 跨大版本的路径处理有变化。开放式下限让"工具链升级"变成一次**静默的破坏性变更**，
而且它藏在几十个其他错误里。

**预防规则**：
> CI 工具链一律用**闭区间或精确版本**（`~3.31.0`），并在注释里写清"为什么选它"。
> "下限"不是锁定。依赖同理：`builtin-baseline` 要锁 commit，Qt 要锁版本。

## 根因六（正面经验）：CI 只装被链接的依赖

`vcpkg.json` 声明 10 个 port，实际被 CMake 引用的只有 `Qt6`、`libsodium`、`GTest`。
Windows 上 `build-test` 单 job 75.6 分钟，其中 **74.6 分钟（98.7%）在编译无人引用的
`openssl` + `libssh`**，导致计划自带的 45 分钟冷启动门禁 P0-A6 **在物理上无法达成**。

改为"CI 只安装树里真正 link 的 port"后：依赖从 51 个包降到 4 个包、65 秒，
整条流水线 **3 分 02 秒**，P0-A6 从不可能变成宽裕达标。

**预防规则**：
> `vcpkg.json` 是唯一事实来源，但 CI 从中**派生**一份更小的清单。
> 派生逻辑用带注释的 SKIP 表写死，并带一条**契约**：任何阶段开始消费某个 port 时，
> 必须在同一个 PR 里删掉它的 SKIP 条目。漏删的代价是几分钟内一个明确的 "not found"，
> 而不是默默编译 75 分钟没人用的库。

## 第二轮：Phase 1 收尾阶段的 7 个新坑

Phase 1 收尾（工作区外壳 + 配置持久化 + CI 内真实 SSH）又踩了 4 个坑。和上面六条不同源：上面是"看不懂日志"，下面是"**日志是对的，是我以为的东西错了**"。

### 7.1 把 sanitizer 和覆盖率塞进同一个构建树 → 217 个假阳性 data race

gcov 的计数器是**普通全局变量**。同一个二进制里同时开 `--coverage` 和 `-fsanitize=thread`，两个线程各自自增同一个计数器，TSan 就把这个自增报成 data race。

本地实测：217 处报告，**全部指向 `__gcov` 符号**，没有一处指向环形缓冲本身。

**预防规则**：
> sanitizer 和覆盖率**永不同构建**。要跑 TSan 就换一棵构建树（`linux-tsan` preset，coverage OFF），
> 且 TSan 步骤放在 job **最后**——它一失败，前面的 build / test / coverage 全被 skip，
> 一轮 CI 白跑，什么证据都留不下。

### 7.2 批量改写脚本把一行 YAML 挪到了别人的 `run:` 里

用脚本做"移动步骤"这类重排时，`if-no-files-found: error` 被切到了下一个步骤的 `run:` 脚本尾部。shell 把它当命令执行 → `command not found` → exit 127。

后果不是"配置写错了"这么轻：**这个步骤里所有已经通过的断言都被这一次退出码抹掉**，job 变红；读日志的人第一眼看到的是 `exit 127`，要往回翻很久才知道真正的测试早就 Passed 了。

**预防规则**：
> 脚本改完 YAML，**先本地解析一遍**（`uv run --with pyyaml python -c
> "import yaml,sys;yaml.safe_load(open(sys.argv[1]))" <file.yml>`，
> `UV_CACHE_DIR=$PWD/.cache/uv`；按规则 2 走 uv，不要用系统 `python3`），
> 再 grep 确认关键行的归属步骤——这比通读一遍 diff 还快。
> 判据：`grep -n "if-no-files-found" ci.yml` 的行号必须落在它该在的那个 step 块内。

### 7.3 fortified libc 把 `memcpy(dst, nullptr, 0)` 判为错误

Linux 上 `-O1` 及以上会开 `_FORTIFY_SOURCE`，于是 `memcpy(dst, nullptr, 0)` 变成编译期错误（`-Werror=nonnull`）。coverage 构建用 `-O0` 把它掩盖住了，于是"本地绿、CI 红"。

**预防规则**：
> C 接口收到"可能为空的指针 + 可能为 0 的长度"时，**在入口显式拒绝空指针**，不要把判断推给 libc。
> 空指针 + 0 长度在标准里是未定义行为，各家 fortified 实现会各自加码。

### 7.4 sshd 用 `UsePAM no` → 公钥认证被拒，却伪装成"密钥不对"

runner 账号的密码字段是锁定的（`!`）。`UsePAM no` 时 sshd 走自己的账户检查，遇到锁定的密码字段直接拒绝，错误信息是笼统的 `authentication failed`——看起来像密钥生成错了，实际上跟密钥毫无关系。

**预防规则**：
> 诊断"认证失败"时，**先确认账号本身能不能被 PAM 认证**，再怀疑密钥。
> 冒烟标记要和命令文本**不一样**：PTY 会回显你输入的命令，标记写死成命令的一部分时，
> 测试会在命令根本没执行的情况下通过——**恒真的测试比没有测试更危险**。

### 7.5 用自己的输出当基线，等于把 bug 一起固化；参考实现也会和标准打架

P1-A2 要"逐项比对基线"。最省事的做法是：跑一遍我们自己的状态机，把结果存下来当基线。

这个做法**什么都没验证**。基线只是我们当时的行为的快照，之后它只会证明"我们没变"。

于是改用 tmux 作独立参考实现。基线一上来就指出一处分歧：`38:2:255:0:0`（冒号写法的
直接色）我们读成红色，而 ITU T.416 的写法是 `38:2:<色彩空间>:r:g:b`，五段——按标准，
四段的这串参数缺少色彩空间槽，应当非法。

我照标准改了实现。然后差分测试朝**反方向**红了：tmux 的基线里那一格是红色的，
说明 tmux 接受四段简写。**标准说 A，主流实现做 B，而产品必须做 B**——终端要和真实
终端对话，不是和标准对话。改动被回退。

**预防规则**：
> 基线必须由**独立实现**产生。tmux 就是现成的参考实现：它对同一批转义序列的处理是独立的，
> 基线因此是"关于序列"的证据，而不是"关于我们自己"的证据。
> 差分测试的价值恰恰在这里——它第一次把我们的实现和另一个实现放在同一张桌子上，
> 而单测永远只能证明我们自己和自己一致。
>
> 但**参考实现是仲裁者，不是真理**：当差分测试和你的标准解读冲突时，先问"产品该匹配谁"。
> 终端匹配的是别的终端。
>
> 顺带两条：
> - 用例**结束时不要清屏**。空屏和任何空屏都相等，测不测都一样。
> - 比对用**文本差异**而不是纯哈希。哈希只说"不同"，人要确认差异时需要看到**哪一格动了**。
>   差异打印本身也要当心：`getline(a) || getline(b)` 会在第一边还有行时短路，
>   另一边留空——**一个只显示空列的 diff 比没有 diff 更误导人**。

### 7.6 差分测试报出差异时，先问是谁错了

第一轮真机差分（vim / htop / less 三个程序）报了"全都不一样"。拆开看，
**三个原因里两个在比较工具本身，一个在产品**：

- 参考解析器**按行重置了 SGR 状态**。tmux 的 capture 是跨行延续属性的，
  换行不是属性变化 → 第一行之后的颜色全被我的解析器丢掉
- 参考解析器**忽略了 SGR 7** → less 的反显状态行在基线里变成普通文本
- 擦除**丢了当前背景色** → **产品 bug**：htop 先设行底色再擦行，
  我们的实现把行底色丢了，**屏幕上直接看得出来**

**预防规则**：
> 差分测试报出差异时，**差异只说明"两边不同"，不说明"谁错"**。先分类：
> - 差异在**画面上看得见**吗？看得见的是产品 bug，去修产品
> - 看不见的（空白格上的前景色、反显的归一化）是**模型差异**，
>   要在比较格式里归一化，而且**两边都要归一化**——只归一化一边，差分全是噪声
>
> 还有一条经验：**参考实现通常在协议上是对的、在格式上是错的**。
> 所以先怀疑自己写的解析器。解析器最常见的三种错：
> 按行重置状态、漏掉某个 SGR、把"模型差异"当成"行为差异"。

### 7.7 判据按缩水的规模测过，就不算测过

P1-A3、A4、A5 三条判据都长期跑在缩水的规模上：解析 2 万行（判据写 100 万行）、
并发 200 万字节（判据写 1000 万次）、回滚工作集 2,000 行（判据写 128,000 行）。
缩水的理由是"共享 runner 要快"。

实测下来这个理由站不住：100 万行解析 10.6 s、14 万行写入 47 ms、1000 万字节在 TSan
下 0.24 s。**加起来不到 15 秒**，而 job 本来就要跑十分钟。更糟的是，归档里这些格子
只好如实写成"未实测"——一个按缩水规模测出来的数字，说明不了判据本身。

**预防规则**：
> 判据里写了规模（多少行、多少字节、多少次），就按那个规模测。
> 共享 runner 的时间预算不够时，**先算一遍要多久**再决定缩不缩：
> 10 秒和 10 分钟是两种结论，别用"估计很慢"代替算。
> 缩了就要在遗留登记里写明"判据字面未满足"，并且**把它当成待办**，不是当成结论。

顺带一条：
> 判据里没被任何测试覆盖的那一项（例如"内存增长 ≤256MB"），先问"这一项有人测过吗"。
> 归档里最容易被漏掉的不是测错的值，而是**根本没测的那一栏**。

## 第三轮：Windows 本地 shell 通道零输出与关闭死锁（第三轮 · 2026-10-24）

### 8.1 子进程的输出出现在 CI 日志里，是被忽略的关键信号

**症状**：Windows 上本地 shell 通道（P1-T10）从头到尾没有任何输出。`LocalPtyChannelTest`
的 5 条用例全红，`MainWindowTest.ALocalShellSessionRunsACommandOnTheScreen` 也红；
POSIX 端全绿。

**定位过程**（4 轮诊断，实际花了 **8 次 CI**——探针是分批加的，每加一批就得等一轮；其中 3 次直接以 600 秒超时收场）：

| 轮次 | 改动 | 结果 |
| :--- | :--- | :--- |
| 1 | 加探针：dump ConPTY 输出管道收到的字节 | 只收到 console host 的 63 字节初始帧（`ESC[2J ESC[m ESC[H` + 标题 + `ESC[?25h`），此后永远为空 |
| 2 | 加探针：子进程是否存活、退出码 | `child alive=0 exit=0`——cmd.exe **立刻**以 0 退出 |
| 3 | 加探针：输入写是否落地 | 写入成功（`written=11`），但没有任何回显 |
| 4 | 回头看 CI 日志本身 | **cmd.exe 的横幅和提示符出现在 CI 日志里** |

第 4 条才是根因所在，而且它一直在眼前：**横幅 `Microsoft Windows [Version ...]` 和
提示符 `D:\a\openSCRT\...\tests>` 都被 CI 日志收走了**。也就是说 cmd.exe 的 stdout 是
**父进程继承来的标准句柄**（runner 的日志管道），它的 stdin 是父进程的 stdin（早已 EOF），
于是它打印完横幅、读到一个 EOF、以 0 退出。

**结论**：通道根本没接上，不是"接上了但没数据"。"没有数据"有无穷多种原因，
"数据去了别处"只有一个原因。

**两次猜错**：

1. 猜"管道句柄要可继承、且要在 `CreateProcess` 之后才释放"（理由是"子进程没 attach 上，
   是 console host 拿不到管道"）——照官方文档改，**症状完全不变**。这一条改动把两处细节
   一次动了，所以它既是一次错判，也是两轮 CI。
2. 最后一轮去读参考实现（Windows Terminal 的 `src/cascadia/TerminalConnection/ConptyConnection.cpp`），
   答案就一行：

   ```cpp
   STARTUPINFOEX siEx{ 0 };
   siEx.StartupInfo.cb = sizeof(STARTUPINFOEX);
   siEx.StartupInfo.dwFlags = STARTF_USESTDHANDLES;   // ← 关键
   ```

   不设 `STARTF_USESTDHANDLES`，子进程就**继承父进程的标准句柄**；设了它且三个句柄留空，
   子进程才会去用伪控制台的句柄。

**验证**：加上这一行之后，run `#39995159095` 的 `unit_local_pty_channel` 从"5 条用例各超时
5 秒全红"变成 **0.33 秒全绿**（命令输出真的回到了通道里），Windows / macOS / Linux 三条
腿加格式检查，4 个 job 全绿。

### 8.2 Win32 的默认行为不能靠记忆

`CreateProcess` 有七个参数，每个都有"不传时的默认行为"，再乘上 `STARTUPINFO` 的标志位组合，
凭记忆推断出来的行为**必然出错**。本次错了一次（句柄可继承 + 释放时机，一个提交两处细节），
第二次靠读参考实现一次读对。**先找官方 sample 或参考实现，再写代码。**

### 8.3 假设要写成一次能判定的实验，而不是一次一改

前三轮都是"改一处 → 跑一轮 CI → 看日志 → 再猜"，每轮 10 分钟。第四轮本来要改成：
**四种 spawn 形状并排跑一次**（不设标志 / 设 `STARTF_USESTDHANDLES` 留空 / 用管道直通 /
临时清空父进程自己的标准句柄），每种形状报告"子进程输出有没有经过控制台"，
一次 CI 就能把候选空间全部覆盖，代价是写一个临时矩阵测试。

**这个矩阵测试最终没派上用场**：它那两轮 CI 先在编译期挂了（见 8.5 的代价分布），
等它终于能跑时，答案已经从**读参考实现**那里拿到了——Windows Terminal 的
`ConptyConnection.cpp` 里就写着 `siEx.StartupInfo.dwFlags = STARTF_USESTDHANDLES;`。
矩阵测试于是被删掉了（临时探针用完要删）。

**留下的教训不是"矩阵测试更好"，而是两条**：
1. **读参考实现比设计实验更便宜。** 答案就在一行源码里，而矩阵测试要写、要编、要等一轮 CI。
   顺序应该是：**先找参考实现 → 找不到再设计实验**。
2. **写下来的实验方案，如果最后没跑成，就不能算作做过的实验。** 这一节原本把矩阵测试
   写成了"第四轮改成"，那是**我记忆里的计划，不是发生过的事**——复盘里混进计划，
   读者会以为那条路走过。写复盘时要分清"做过的"和"打算做的"。

**顺带修正的一条认知**：`CreatePseudoConsole` 成功、`UpdateProcThreadAttribute` 成功、
`CreateProcess` 成功——**三者都不代表子进程 attach 成功**。这个失败是完全静默的：
没有错误码，没有对话框，子进程只是安安静静地用继承来的句柄跑起来了。

### 8.4 一个两轮 CI 里出现两次的挂死，和一次错误的归因

`unit_local_pty_channel` 在 Windows 上**这一段 8 次 CI 里有 3 次以 600 秒超时收场**，
每次都是 `***Timeout 600.01 sec`，每次都停在同一条用例（`cmd.exe /c echo` 那个）之后。

**第一轮归因是错的。** 第一轮我改了 `disconnect()` 里的顺序（先 join 读线程、再关句柄），
第二轮 CI 照样挂——**而且第二轮用的是原来的顺序**。也就是说这个挂死跟我的改动无关，
它是既有代码里的一个竞态，第一轮只是碰巧撞上了。

**真正的定位靠的是探针的最后一行。** 给读线程与关闭路径都加了生命周期探针之后，
日志里挂死前的最后一行是：

```
[probe] closing the pseudo console
```

——测试进程卡在 `ClosePseudoConsole()` 里面。而微软文档早就写了这句：

> The act of closing the pseudoconsole session may emit a final frame update to `hOutput`
> **which should be drained from the communications channel buffer.**

关闭伪控制台时，console host 会往输出管道写最后一帧，`ClosePseudoConsole` **等这一写完成**。
而这条路径是**先停读线程、再关控制台**——没人再消费那个管道 → 关闭动作永远等不到写完成 →
**死锁**。

正确的顺序是反过来的：**读线程还在消费的时候关闭伪控制台**，等 console host 退出、
管道到 EOF，再停读线程。改完之后这条用例连跑二十次都不挂。

**两条教训**：

1. **"我刚改的地方"不等于"根因"。** 第一轮的改动让挂死"看起来"是新引入的，但第二轮
   用旧顺序复现了它。**同一个症状在两轮里都出现，就说明它不是那一轮改出来的。**
2. **探针的最后一行比推理可靠。** 前面三轮都在推理"读线程卡在哪"，加了探针之后
   一行日志就把答案摆出来了。**挂死类问题，先让程序说出它停在哪一步。**

### 8.5 发布流水线的四个新坑

**一、发布页只拿到一个平台的资产。** `publish` 写成 `needs: package-windows`，于是它一
等 Windows 结束就开始跑，`download-artifact` 执行的时候 macOS 与 Linux 还在打包 → 资产
没上传 → **v0.1.2 的发布页上只有 Windows 的两个文件**。修法是三件事一起改：
`needs: [package-windows, package-macos, package-linux]` 让它等齐，
`if: always() && startsWith(github.ref, 'refs/tags/v')` 让某个平台失败时不至于把整个
发布拖垮（已经打出来的资产照发），下载步骤用 `pattern: openSCRT-*` + `merge-multiple`
把三个平台的产物收进同一个目录。

**二、vcpkg 的 triplet 是架构决策，不是平台决策。** macOS 的打包任务按"macOS 就是 x64"
写了 `x64-osx`，而 **macos-14 的 runner 是 Apple Silicon**。vcpkg 老老实实把 `libssh`
编成了 x86_64，链接器最后一步拒绝把 x86_64 的 `.a` 链进 arm64 的目标：

```
ld: warning: ignoring file '.../x64-osx/lib/libssh.a': found architecture 'x86_64',
    required architecture 'arm64'
```

**平台名不蕴含架构**，尤其在 CI 的 runner 镜像上——直觉会骗人，链接器不会。
改用 `arm64-osx` 之后，包在 Apple Silicon 上原生运行，不用 Rosetta 2。

**三、macOS 的 `.app` 是自己组装的，`macdeployqt` 不能照搬。** 又两轮失败：

1. `macdeployqt <裸可执行文件> -appbundle` 报 `Could not find app bundle`——它要的输入是
   一个**已经存在**的 `.app` 目录，而不是一个二进制。
2. 自己组装 bundle 时，用 `otool -L` 遍历链接关系来推断该带哪些 framework，漏了
   `QtDBus.framework`（QtGui 链的是它），启动即
   `Library not loaded: @rpath/QtDBus.framework`。

**最后是"全带上"**：把 Qt 安装目录下的 framework 全部复制进 `Contents/Frameworks`，
用 `install_name_tool -add_rpath @executable_path/../Frameworks` 把加载路径指回 bundle 内，
再手工复制运行时才加载的平台插件到 `Contents/PlugIns/platforms`，最后写一个 `Info.plist`。
**framework 的集合不要靠推断**——推断错一个就是启动即崩，而且只有真正启动一次才会发现。

**四、发版前先把打好的包在 runner 上跑一遍。** 打包步骤现在在打 tar 之前执行一次
`--self-test`：一个在构建它的机器上都起不来的包，没有资格发布。上面那两轮 macOS 的失败
都是这一步本该拦住的。

## 第四轮：纪律本身也要能被检查

2026-10-24 这一轮，`AGENTS.md` 里刚写下的规则 0（CI 红着不要推 main）、规则 2（Python 走
uv）、规则 3（外网走代理），**在同一轮里全被违反**：CI 还红着就连推了两次 main、拿系统
`python3` 改文档、改 release body 的请求没走代理。GitHub 侧的时间戳把这三次都记着。

**三条规则没有一条拦住我**——它们写下来了，但没有任何检查点。所以这一轮给每条配了一个
能做的动作（见 `AGENTS.md` 的「纪律的自查」）：推之前先查上一个 run 的结论、跑 Python 用
`uv run`、每条外网命令都 `source ./.proxy.sh`。

**教训**：写下来的纪律如果没有检查点，就只是愿望；**能被检查的纪律才算纪律**。
这也是"先分类"那一条的延伸：一条规则如果只在出问题之后被想起，它就不是规则，是事后总结。

**还有一条更基础的**：这一轮的很多返工，是在**把记忆里的事实搬回仓库**——代价分布表的数字
是凭印象写的，8.3 把一个没跑成的实验写成了"做过的办法"，8.4 的"四轮挂两轮"与日志不符。
**会话记录会被截断，仓库不会。** 所以复盘里的每一个数字、每一处措辞，都要能在仓库里
指到出处（run 链接、日志、git 历史）；指不到出处的，宁可写"没查"也不要写一个看起来
合理的数。读者会把复盘当证据看，证据不能靠回忆。

**同一条纪律还有第二种形状：报告 ≠ 门禁。** README 写着 Windows 的系统版本下限
"由导入表门禁实测，不是从文档抄的"——读起来像是有人守着。但门禁当时的实现是：我们自己的
二进制走 `--strict`（超了构建失败），**Qt 库只走 `--report`（超了只打印一行）**。于是"实测"
只覆盖我们自己写的代码，**发布包的地板从来没有人卡过**：Qt 一次升级把地板抬到 1903，
CI 照样全绿，而承诺（"Windows 10 1809 or later"）是在用户机器的加载器里破掉的，
在 `main()` 之前，只弹一句"找不到入口点"。

同一个洞的形状和上面那条一模一样：**声明比检查强**。而这次的诱因尤其值得记下来——
错的不在代码，在**文档与门禁的措辞对不上**：`README.md` 说"实测"，CI 步骤里写的是
"reported rather than enforced"。两句话都在仓库里，谁也没把它们放在一起看。

**预防**：凡是文档里出现"由 CI 保证""由门禁实测""CI 会拦住"这种措辞，就去核对那个 CI 步骤
到底是 `--strict` 还是 `--report`；报告和门禁的差别只有一行，但差别就是承诺能不能兑现。
`--package-floor` 就是为这条加的（`8769bde`），它让发布包的地板也变成会红的门禁。
（阈值后来随决定 0001 一起从 1809 变成 **1607**：Windows 2016 要能用，Windows 的构建因此
改用 Qt 6.7 —— 门禁的数字必须跟承诺的那个数字一致 ✔。）

**同一条纪律的第三种形状：门禁存在，但它在别人的机器上跑。** clang-format 的门禁每轮都在，
我每轮都知道它在那儿——但推之前没有在本地跑一次格式化，于是 Phase 2 的第一个提交
（`26cd612`）被 format job 拒了，白付一轮 CI。格式化是**规则 1 明文允许的本地动作**
（"本地只写代码、格式化、提交"），所以这不是"本地不能做"，是我没做。

修法不是"以后小心点"，是把它写成一个能做的动作：**用钉住的版本**（CI 跑的
`clang-format==23.1.3`）在本地 `clang-format -i`。用别的版本格式化等于把代码改成另一个
样子，CI 照样红——而本地又没有编译器能告诉你这件事。`AGENTS.md` 的自查表因此多了一行。

同一轮里还暴露了另一个习惯问题：**我写的断言，可能比实现更自信**。那个失败的测试断言
`isAvailable()` 在 `lock()` 之后应为 false，而 fake 实现只清了条目——接口文档写的是
"can answer right now"，所以是 fake 错了。教训：**测试失败时先问"谁错了"**，别默认实现
是对的、是自己看错了。

**还有一类门禁是"你以为它是这样"。** `.gitattributes` 里 `tests/fixtures/** text eol=lf`
规定了行尾归一化——那条规则本身是对的（Windows runner 的 `core.autocrlf` 会把 VT 夹具的
字节改掉，一个多余的 CR 会把光标拉回第 0 列），但它**没有区分文本夹具和二进制夹具**。
结果是新的 `.kdbx` 夹具入库时被归一化，两个字节变成一个，文件不再能解密。

症状很隐蔽：文件在，测试在，CI 也会照常跑——只有"能不能解开"会暴露。**预防**：二进制夹具
要在 `.gitattributes` 里显式标 `binary`，并且把来源文件的哈希写进夹具的 README；入库后
对一次哈希，比读日志快。这和根因一是同一个形状：**"工具报告成功"不等于"产物在预期位置"**，
这里连位置都是对的，错的是内容。

## 第五轮：触发器也是门禁的一部分（2026-10-25）

CI 的触发器一直没有路径过滤，于是**每推一次文档就烧掉一整轮三平台矩阵**：build-test 在
ubuntu / windows / macos 三个 leg 上重新走 vcpkg 与 Qt，最贵的一腿 45–60 分钟——用来证明
一句话没有把构建搞坏。

修法有两种，差别比想象的大：

- **job 级门禁**：让每个 job 自己判断"这次改的全是文档吗，是就跳过"。CI 仍然产生一个
  run，只是 job 秒绿。**省下的时间是真的**，但 main 上仍会挂着一个 run。
- **触发级 `paths-ignore`**：让 workflow 根本不触发。**连 run 都没有**。

这里选了后者：本仓库直推 main、没有分支保护，main 上多一个秒绿的 run 没有价值；而
"这个提交不需要三平台验证"这件事，写在触发器里比复制到每个 job 里更不容易漂。

**忽略清单必须窄。** 只有能证明**不在构建图里**的东西才能进去：

| 忽略 | 为什么它不在构建图里 |
| :--- | :--- |
| `'**.md'` | 全仓库 7 个受版本控制的 `.md` 都是文档；构建与测试**没有一个读它们**（C++/CMake 里对 `.md` 的引用全是注释）。`tests/baselines/vt/README.md` 早被漂移比对显式排除 |
| `'docs/**'` | 文档目录，现在没有别的，以后放图片也一样进不了构建 |
| `'.proxy.sh'` | 本地辅助脚本，`.github/` 里没有任何地方引用它 |

**刻意留在清单外**的：`.gitattributes`（决定 checkout 后的行尾，能改源码）、
`.gitignore`（决定打包步骤收进哪些文件）、`.github/**`（这就是 CI 本身）、
`vcpkg.json` / `CMakeLists.txt` / `src/**` / `tests/**`——少写一条，就多一份"这次改动其实
该验证却没验证"的风险。

**两个坑，都踩过了：**

1. **`'**/*.md'` 不够。** 它里面的 `/` 是字面量，匹配不到根目录的 `README.md` 与 `AGENTS.md`。
   GitHub 文档里的写法是 `'**.js'`——"匹配仓库里所有 .js 文件"，例子同时列了根目录的
   `index.js` 和 `src/js/app.js`。**写下来之前去查文档，不要凭印象写 glob。**
2. **`pull_request` 不能加同样的过滤。** 被路径过滤跳过的 workflow 不会报出它的 required
   status check，将来一旦开分支保护，文档类 PR 的那个 check 会永远停在 pending。本仓库
   现在直推 main、没有 PR 保护，所以 PR 触发器留着不加过滤——它是给未来的评审流程用的，
   那天它必须是无条件的。`workflow_dispatch` 同样保留，人工随时能跑完整矩阵。

**代价**：纯文档提交不再产生 run，于是"推之前查上一个提交的 run 结论"这条纪律**对文档提交
没有 run 可查**。AGENTS.md 的自查表相应改成"查最近一次**真实** run"，并写明要用
`?head_sha=<sha>` 查某个提交自己的结论。

**证据**（正反两条都要有，缺一条就分不清"过滤生效了"和"workflow 坏了"）：

- **正向**：改 `ci.yml` 本身属于非文档改动，必须照旧触发完整矩阵——run **#40120776915**
  （`a8bfa7d`）四个 job 全绿。
- **负向**：纯文档提交 `c22b514`（同时动根目录的 `AGENTS.md` 与 `docs/` 下的两个文件）推送后，
  `GET /actions/runs?head_sha=c22b514` 返回 **`total_count: 0`**——推送后 35 / 70 / 105 / 140 秒
  各查一次都是 0，仓库里最新的 run 始终是 `a8bfa7d` 那条绿的。**它同时动根目录和 `docs/`**，
  是故意的：根目录那个只有 `'**.md'` 能盖住，`docs/**` 盖不住——所以这条证据测的是 glob
  语义本身，而不是"反正 `docs/` 里有东西"。**只查一次不算数**：run 可能迟到，隔几分钟
  再查，否则分不清"没有 run"和"run 还没来"。

## 第六轮：Phase 2 的新坑（2026-10-25）

### 9.1 一轮 CI 只报第一个错误，后面的错误藏在后面

Phase 2 的一次推送里有两个错：导入器的测试没点名 `Qt6::Core`（`No such file or
directory: 'QDir'`），窗口里的 `KdbxVault::opened` 少写了命名空间。

**Windows 和 Linux 两条腿只报了第一个**——构建在那个目标上停住，轮到
`MainWindow.cpp` 的编译根本没开始；只有 macOS 那条腿把两个都报了出来。

同一个错在三条腿上表现不同，**看起来像三个不同的错**。差点按"平台差异"去查，而真相
是 ninja 在第一个失败处停下（`-k 1`）。

**做法**：一轮失败后把日志里**所有**编译错误一次修完再推，不要一个一个改一个推。
分平台"表现不同"的编译错误，先怀疑是"谁先失败"，不是"平台不一样"。

### 9.2 Qt 的类里埋着会撞车的成员名

`QWidget` 有个 protected 成员就叫 `data`（`qwidget.h`）。在 `QWidget` 的子类里写一个
叫 `data` 的局部变量或参数，`-Wshadow` 会直接拦下——而本仓库 `-Werror`，于是就是编译
失败。

缓冲区改叫 `payload` / `bytes`。**教训**：Qt 的头文件里埋着这种名字，`-Wshadow` 比人
眼更容易撞上它们；本地不编译的仓库里，"看起来无害的变量名"是一整轮 CI 的价钱。

### 9.3 成员的类型名不进入作用域；私有依赖要由用到它的测试自己点名

两件小事，一件是名字，一件是链接：

* `MainWindow` 有个成员 `credential::kdbx::KdbxVault vault_;`，但**成员不会把类型的
  名字带进作用域**。写 `&KdbxVault::opened` 是不行的，要写全
  `&credential::kdbx::KdbxVault::opened`。
* `openscrt_config` 把 `Qt6::Core` 链成 **PRIVATE**（它自己的头文件不提 Qt，这是对的）。
  于是**用到 Qt 的测试必须自己点名 Qt**——测试不属于库的"使用者"，库不会替它把 Qt 的
  include 路径带过去。

### 9.4 格式跟记忆不符时，基线要由独立实现产出（第二次吃到这个亏）

写 SecureCRT 导入器时，我记的是"`[Connection]` 段的 INI、键名 `HostName`、十进制端口"。
核对下来**三条全错**：SecureCRT 的会话文件是扁平的带类型前缀的键值
（`S:"Hostname"=…`、`D:"[SSH2] Port"=00000016`），端口是十六进制的 DWORD。

这和 KDBX 那次是同一件事（`docs/evidence/kdbx-format-notes.md` 记了七次记错的），
所以用了同一套做法：**真实文件 + 两个互相独立的实现**（RustConn 的导出器、oryxis 的
导入器）三方对齐后才动手，每条事实带出处记进
`docs/evidence/securecrt-config-notes.md`。

真实文件因为来源仓库**没有许可证**而没有入库，只在本地留副本核对——测试用的夹具是按
核对出来的格式自己写的。

### 9.5 格式化器能改坏代码
Windows 那条腿的失败是：**clang-format 把 `<wincred.h>` 排到了 `<windows.h>` 前面**。
`wincred.h` 用 `windows.h` 的类型（`ULONG_PTR`、`DWORD`、`LPWSTR`）却不自己包含它，
于是它在一个什么都没有定义的环境里被解析，编译器报的是
`'dwLower': unknown override specifier` —— 看着像"类型写错了"，其实是"类型根本没定义"。

**格式化器改的是代码，不是风格**。两个 include 之间放一行注释，它就不会重排它们；
仓库里 `LocalPtyChannel.cpp` 的 `windows.h` / `consoleapi.h` 早就是这么写的（为了
`CreatePseudoConsole`），只是当时没人把"为什么"写下来。

**教训**：SDK 的头文件常常**靠包含顺序**。凡是要包含 Windows SDK 的头，就把顺序和
理由写进注释里，别指望格式化器懂。

### 9.6 无界的等待会把 UI 线程挂死

macOS 那条腿在 `ClosingAPaneClosesTheSessionsInIt` 里卡了十分钟，被超时杀掉。原因是
一行 `waitpid(child, &status, 0)`：**没有期限的等待子进程**。macOS 上的 shell 没有
因 SIGHUP 退出，这个等待就一直挂着——**而它挂在画窗口的那个线程上**。

同一个文件里已经有两处"等待必须有期限"的写法（ConPTY 的 `WaitForSingleObject(handle,
2000)` ✔、读线程的 `poll(…, 200)` ✔），偏偏这一处漏了。

**教训**：**凡是 join / waitpid / wait 都要有期限**，否则一个不听话的子进程就能把整个
界面冻住。期限到了就杀掉它（还没被 reap 的子进程是僵尸，内核不会把僵尸的 pid 发给
别人，所以 kill 不会误伤 ✔）。

**同一轮里还有两个测量本身的问题**，一并记在这里：

* **量"卡顿"要量事件循环自己忙了多久**，不要量两轮之间的间隔——间隔里还夹着测试自己
  的休眠，而 Windows 上 1 ms 的 `sleep` 实际会睡 15.6 ms（系统时钟粒度）✔。
* **扫进程的内存只能读可写的映射**。整个地址空间里最大的是库文件，读一遍要 600 秒；
  而明文只可能写在可写内存里 ✔。另外读内存要用 `pread` 而不是流：流有自己的缓冲区，
  那份缓冲区会留下上一次找到的东西，第二次扫描就会"找到"一个并不存在的明文 ✔。

### 9.7 编译错误要读 note 行（macOS 的 mach_vm_region 连错三轮）

macOS 那条腿为了让测试能扫自己的进程内存，要调 `mach_vm_region` ✔。**同一个错误连着错了
三轮** ✔：

1. `reinterpret_cast from 'vm_region_basic_info_data_64_t' to 'vm_region_info_t' is not
   allowed` —— 联合体是按值传的，我按值转 ✔；
2. `no matching function for call to 'mach_vm_region'` —— 改按指针转之后，**参数个数不对** ✔；
3. 还是 `no matching function` —— note 里写着 `no known conversion from 'vm_address_t *'
   to 'mach_vm_address_t *'` —— **地址要用 mach_vm 那套类型** ✔。

三轮的答案一直写在错误下面那行 `note:` 里 ✔：`requires 7 arguments, but 6 were provided`
✔、`no known conversion from ... to ...` ✔。

**教训**：

- **读 note 行，不只读 error 行** ✔ —— clang 把"要什么"说得很清楚 ✔；
- **镜像里的 SDK 可能是旧的** ✔：网上的 `MacOSX10.6.sdk` 里 `mach_vm_region` 是七个参数、
  info 是 `vm_region_info_t` ✔；runner 上装的是 14.5 ✔，七个参数 ✔、info 是
  `vm_region_info_data_t *` ✔、地址是 `mach_vm_address_t *` ✔。**裁判是 runner 上装的那份**
  ✔，不是网上的 ✔；
- **同一个错误连着两轮症状不变就停下来读日志** ✔ —— 第三轮之前把错误和 note 完整读一遍，
  就是一行改动 ✔，而不是再猜一轮 ✔。

### 9.8 探针一行都没打出来 = 崩在被调用的内部；出参不能传 NULL

macOS 那条腿的内存扫描，编译一次就过了，跑起来 **SIGSEGV** ✔。三轮才找到地方 ✔：

1. **第一轮**：猜"映射太大读崩了" ✔ → 把扫描范围改成只读可写映射 ✔ → **还是崩，一模一样** ✔；
2. **第二轮**：猜"`mach_vm_read` 的计数单位是元素不是字节，填错就是 8 倍越界" ✔ → 换成
   `mach_vm_read_overwrite` ✔ → **还是崩，一模一样** ✔；
3. **第三轮**：上探针（每走一步打印一行）✔ → **一行都没打出来** ✔ → 崩在**第一次
   `mach_vm_region` 调用内部**，函数根本没返回 ✔。

第三轮的行数是判据 ✔：**探针的输出停在调用之前 = 崩在被调用的里面** ✔。

根因：`mach_vm_region` 的第七个参数是"这个区域背后的对象名"，是个**出参** ✔。
**内核那侧查了指针**（xnu `osfmk/vm/vm_map.c`：`if (object_name) { *object_name = IP_NULL; }`）✔，
**客户端桩那侧不开源、看不了** ✔ —— 但症状说明它不查 ✔：它把 reply 里收到的端口名**直接往
用户指针里写** ✔。我们传的是 `nullptr` ✔ → 往地址 0 写 → **SIGSEGV** ✔。

**所有真实调用点都传真实变量**：CPython 的 `Python/remote_debug.h` ✔、Rust 的 `mach2` crate ✔、
Zig 的 `lib/std/c/darwin.zig` ✔、Chromium 的 `base/process/memory_mac.mm` ✔ ——
**一个传 NULL 的都没有** ✔。

**教训**：

- **出参别传 NULL** ✔ —— 内核查不等于桩也查 ✔，同一份协议的**两端要分别读** ✔；
- **"内核怎么实现的"和"客户端桩怎么实现的"是两回事** ✔ —— 内核在 `vm_map.c` ✔，
  桩在 libsystem_kernel（不开源）✔，只能靠**真实调用点**反推 ✔；
- **探针的输出停在哪里，就说明崩在哪里** ✔ —— 零输出 = 崩在被调用内部 ✔；
- **自己写下的根因没被证据打中就要改** ✔ —— 第二轮那套"8 倍越界"的解释是**错的** ✔
  （崩点在遍历区域那一步，压根没走到读内存那一步）✔。**照抄进复盘会教错人** ✔；
- **"顺手做的优化"和"根因"要分开写** ✔ —— "只读可写映射"治的是**读得慢** ✔，
  不是治崩溃 ✔。

### 9.9 macOS 上挂死 600 秒：日志说它停在哪一步

2026-10-25 夜，macOS 那条腿的 `unit_workspace_panes` **撞满了 600 秒的用例上限** ✔，
而这一轮**没有任何代码改动**（只有脚本和文档）✔ —— 所以它是**偶发**的 ✔，而且只在 macOS 上 ✔。

**日志怎么说** ✔：挂住之前的那个用例 0 ms 通过 ✔，挂住的那个用例**连开始都没有打印结果** ✔
—— `WorkspacePanesTest.ClosingASessionLeavesThePaneItWasIn` ✔，也就是**关掉一个本地 shell
会话**的时候 ✔。往前一条日志是 Qt 自己说的 ✔：

```
QSplitter::replaceWidget: Widget can't be null
```

**三处都能证** ✔：

1. **fd 竞态** ✔：本地 shell 的读线程 poll 的是 master 描述符 ✔，而关闭路径**先关描述符、
   再停读线程** ✔。**在阻塞的 read 底下关掉描述符是未定义行为** ✔，而且那个编号可能已经被
   别人拿走了 ✔ —— 读线程于是等在一个跟这个 shell 毫无关系的文件上 ✔，`join` **永远不返回** ✔
   （POSIX 分支现在**先停读线程、再关描述符** ✔；读线程一个 poll 周期内就会看到停止 ✔）。
   **Windows 那条分支的顺序相反是有原因的** ✔（见 8.1）✔，别把两边的顺序抄串了 ✔；
2. **无期限的等待** ✔：`TerminalSession::close()` 里等"已经在路上的回调"结束的那句
   `guard_->idle.wait(...)` **没有期限** ✔，而注释写的是"这个等待不会挂" ✔ —— 那是**希望，
   不是保证** ✔。本仓库的规矩是**一切等待都有期限** ✔，现在它有了 ✔；
3. **`QSplitter::replaceWidget(index, nullptr)` 根本不管用** ✔：Qt 的实现直接拒绝 ✔
   （"Widget can't be null" ✔）✔，所以那个窗格**从来没有被从 splitter 里拿走** ✔——它只是从
   列表里没了 ✔，树里还留着一个死窗格 ✔，布局还在给它留地方 ✔。现在是把窗格**重新挂到没有人
   的地方** ✔，并且有一条测试说 splitter **真的少了它** ✔。

**教训**：

- **Qt 的告警不是噪音，是证据** ✔ —— "Widget can't be null" 这一行直接指出了三处里的一处 ✔；
- **"这个等待不会挂"是一句需要证据的话** ✔ —— 注释里的断言要么有期限，要么有测试 ✔；
- **关闭顺序要分平台想，别把一边的顺序抄到另一边** ✔；
- **偶发的挂死要靠日志定位，不靠推理** ✔ —— 日志说"哪个用例没打印结果"，就把范围缩到一个
  用例 ✔，缩到一条关闭路径 ✔；
- **仓库里的规矩：等就要有期限，关就要有顺序** ✔。

**教训**：

- **"写下来的纪律如果没有检查点，就只是愿望"** ✔ —— 这句话本来就在纪律自查表里 ✔，
  但自查表里"实际要做的"仍然只是"先查一下最近一次 run 的结论" ✔——那还是靠自觉 ✔；
- **热修链是最容易破纪律的场景** ✔ —— "改一行、推一次"太顺手 ✔，而每一次推都让 main

- **补救要有工具** ✔ —— 现在有 `tools/pre_push_check.sh` ✔：读最近一次真实 run 的结论 ✔，

- **检查点自己也必须能失败** ✔ —— 脚本拿不到 token 或 jq 时**停下来报错** ✔，不猜 ✔：
  一个会猜的检查点比没有检查点更糟 ✔。

## 下次怎么做得更快

1. **失败先分类**：环境 / 编译期契约 / 运行时逻辑。分类错了，后面所有努力都是浪费。
2. **同一处失败连修两轮症状不变 → 停止推理，进观测模式**。加一行 `ls` / `printenv` 的成本，远低于再猜一轮。
3. **每个假设写成可证伪的形式**，再去看日志。
4. **测试红了先分诊**：断言错 vs 实现错，逐条写理由。
5. **改动和判断一起提交**：commit message 里写清"为什么是这个根因"，它就是下次的排查索引。
