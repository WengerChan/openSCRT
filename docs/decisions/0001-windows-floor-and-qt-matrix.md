# 决定 0001：Windows 地板与 Qt 版本矩阵

**状态**：**第 1 节的问题已测出答案**；第 3 节的选择仍待定
**相关**：[`docs/evidence/windows-import-tables.md`](../evidence/windows-import-tables.md)、
[`docs/DEVELOPMENT_PLAN.md`](../DEVELOPMENT_PLAN.md) §4 R10、README 的「Why Windows 10 1809」

## 1. 要决定的是什么

**有没有哪个 Qt 版本，它的包地板还是 Windows 10 1607？**

证据文件的原话是："A Qt build without it would put the package's floor at 1607; the Qt
version matrix question is whether one exists."

- 有 → 可以出一个支持 1607 的包 ✔
- 没有 → 1809 就是最终地板，矩阵这件事不存在 ✔

## 2. 已经量出来的事实

| 事实 | 数值 | 怎么来的 |
| --- | --- | --- |
| 我们自己的 `openscrt.exe` 的地板 | **1607** | ConPTY 的三个入口点改成运行期解析 ✔ 导入表里没有了 ✔；CI 门禁 `--floor 1607 --strict` 卡着 ✔ |
| 整个发布包的地板 | **1709** | `Qt6Core.dll` 导入 `SetThreadDescription` ✔，而真机的 1607 kernel32 **不导出**它 ✔ |
| 我们承诺的支持基线 | **1809** | Qt 6.8 官方自己支持 1809 及以后 ✔；1709 那台机器很可能能启动，但**不是我们支持或测试的配置** ✔ |
| 代码是否用了 6.8 专有 API | **没有** ✔ | `QKeyCombination`、`QStringDecoder` 等都搜不到 ✔ |
| 构建是否写死了 Qt 最低版本 | **没有** ✔ | `find_package(Qt6 REQUIRED COMPONENTS Core)` ✔，老 Qt 找得到 ✔ |

两个门禁都是 **strict**：自有二进制超过 1607、发布包超过 1809，都会让构建失败 ✔。
README 与发布说明里写的数字，就是这两个阈值 ✔。

## 3. 测量结果：**有，而且有三个**

run **#40205287033**（workflow `qt-floor-report` ✔，手动触发 ✔）测了 6.x 每个系列的最后
一个版本，读的是 kernel32 导出表，不是文档 ✔：

| Qt | 包的导入地板 | 结论 |
| --- | --- | --- |
| 6.5 | build 14393 = **1607** ✔ | 1607 地板 ✔ |
| 6.6 | build 14393 = **1607** ✔ | 1607 地板 ✔ |
| 6.7 | build 14393 = **1607** ✔ | 1607 地板 ✔ |
| 6.8 | build 16299 = **1709** ✔ | 抬高地板的是 6.8 ✔ |

**所以问题是"有没有"——有，6.5/6.6/6.7 都可以** ✔。矩阵是可行 ✔，第 4 节的三条路都还在桌上 ✔。

## 4. 三条路

### A. 保持 1809（现状）

- **代价**：0 ✔
- **后果**：1607 的机器装不了 ✔。已经有人因为这个报过问题（v0.1.1 在 1607 上"启动即崩" ✔）✔
- **不承诺的东西**：我们连 1607 的真机验收都还没做（见 DEVELOPMENT_PLAN 的 P1-A7 ✔）✔
- **但现在多了一条**：**不是"我们不测 1607"，而是"没有哪个 Qt 能跑在 1607 上"**——这条已经不成立了 ✔，
  6.7 可以 ✔。不选它的理由要重新给 ✔

### B. 整个包降到 1607（所有 Windows 包都用老 Qt）

- **代价**：Qt 版本被冻结在 6.7 ✔，直到有人决定升 —— 期间**拿不到新 Qt 的缺陷修复与安全修复** ✔
- **后果**：所有 Windows 用户都拿到老 Qt ✔（不只是 1607 的那批人 ✔）
- **承诺**：1607 ✔ —— 而这个承诺**没有真机可测** ✔，只有导入表这一个证据 ✔

### C. 出两个 Windows 包（1809+ 用 Qt 6.8，1607 用 Qt 6.7）

- **代价**：Windows 的发布作业多一条腿 ✔（约多 10 分钟 ✔）；**CI 的 Windows 腿也要多一个 Qt 版本** ✔
  （否则"能编过"只是假设 ✔）；导入表门禁要按产物分两个阈值 ✔（现在的 `--package-floor`
  是一个全局阈值 ✔）；文档要说清哪个包是哪个 ✔
- **后果**：主力用户继续拿新 Qt ✔，1607 的用户拿到一个**不再维护**的构建 ✔
- **维护的尾巴**：老 Qt 那条分支以后要单独维护 ✔（安全更新要手工往回带 ✔）

## 5. 倾向

**先看 §3 的测量结果：6.7 是能跑 1607 的最新版本** ✔ —— 这让选项 C 成为一个真正的选择 ✔
而不是理论上的 ✔。

倾向 **C** 而不是 B ✔：主力用户不该为了少数旧机器被冻结在老 Qt 上 ✔，而 B 的好处
（只有一个包）只对"绝大多数用户都在 1607"这个前提成立 ✔ —— 前提看起来不成立 ✔。

**C 的前置条件**：1607 的需求是真的 ✔ —— 现在只见过一份外部反馈 ✔，值得先问那位报问题的
用户还在不在用 ✔，以及他们能接受一个不再维护的构建 ✔。**这个问不清楚，C 就不该开始** ✔。

**B 只有在"绝大多数用户都在 1607"这个前提成立时才是对的** ✔。

**另外无论选哪条，1607 的真机验收都还没有** ✔（P1-A7 ✔）。承诺一个测不了的地板，
哪怕测量说它行，也没有意义 ✔ —— 选 C 之前应该先有一台 1607 的机器 ✔。
